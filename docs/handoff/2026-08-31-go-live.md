# Making today's three fixes live

Every command below writes to production. Run them yourself (`! <command>` in the session puts the
output here). They are ordered — later steps depend on earlier ones.

Stop and read the output of each. If a count is wildly different from the one written here, say so
rather than continuing: it means the shape of the data has changed since this was written.

---

## 1. The photos — the urgent one  (~5 minutes)

**What is wrong:** 139 items across blummier (136), chill-boutique (2) and feathers-boutique-vintage
(1) are flagged "photos copied" while every one of their photos still sits on `cdn.shopify.com`.
**964 photos.** The copier only looks at items NOT flagged, so it skips them forever — which is why
the fleet prints "0 photos copied" and looks healthy. If any of those sellers cancels Shopify, those
listings go completely blank, not partially.

The code fix is already in (`sameImagesAlreadyCopied` now requires the stored photo to actually be
on our storage). These two commands repair the items that are already stuck.

```
node --experimental-strip-types --env-file=.env.local scripts/reset-false-photo-markers.mts --write
```
Expect: **139 markers cleared.** Nothing is downloaded yet; this only tells the truth about what
still needs copying.

```
node --experimental-strip-types --env-file=.env.local scripts/copy-product-photos.mts blummier --write
node --experimental-strip-types --env-file=.env.local scripts/copy-product-photos.mts chill-boutique --write
node --experimental-strip-types --env-file=.env.local scripts/copy-product-photos.mts feathers-boutique-vintage --write
```
Expect: blummier reports ~136 items complete and ~953 photos copied. The other two are 2 and 1 item.
If blummier reports "0 items complete", the marker reset did not run — go back a step.

Check it worked:
```
node --experimental-strip-types --env-file=.env.local scripts/blackout-check.mts blummier --port 3000 --label live
```
Expect: **SURVIVES cancellation unchanged** on all three pages. Before this it was 0 of 3.

## 2. The rail order and the empty categories  (~2 minutes per store)

**What is wrong:** which products a homepage rail shows, and in what order, was frozen on import day.
bag-crush's homepage still opens with three bags she has sold. Separately, fifteen of
shop-vintage-charm's categories show six pieces each that she emptied months ago, because we could
not tell "we have never read this category" from "we read it and it is empty".

Both fixes are in the code. They take effect the first time a repair runs against a store, because
that is when we re-read her collections and record which ones we actually read.

```
node --env-file=.env.local --import tsx scripts/repair-store.mts bag-crush
node --env-file=.env.local --import tsx scripts/repair-store.mts shop-vintage-charm
node --env-file=.env.local --import tsx scripts/repair-store.mts chill-boutique
node --env-file=.env.local --import tsx scripts/repair-store.mts feathers-boutique-vintage
node --env-file=.env.local --import tsx scripts/repair-store.mts we-thieves
node --env-file=.env.local --import tsx scripts/repair-store.mts ascensio-demo
node --env-file=.env.local --import tsx scripts/repair-store.mts thenicheshop
```
Watch the `order` line: it now says how many collections were ordered **from the live feed** rather
than from the capture. If it says 0 from the live feed on a Shopify store, the read was throttled —
run that store again later rather than accepting it.

Then look at bag-crush's homepage. It should open with the Louis Vuitton Looping, not with three
sold Guccis.

## 3. Prove the empty-categories fix is actually on

It is the one that fails quietly if the database column was never created. The code now creates the
column on demand and warns in the logs if it cannot — but check it directly once:

```
node --env-file=.env.local -e "const {neon}=require('@neondatabase/serverless');(async()=>{const s=neon(process.env.DATABASE_URL);console.log(await s\`SELECT count(*)::int total, count(members_synced_at)::int stamped FROM collections\`)})()"
```
Expect `stamped` to be greater than 0 after step 2. **If `stamped` is 0, the fix is not live** — every
collection page is still serving its crawl-day snapshot, whatever the code says.

## What is NOT in here, and why

- **shop-vintage-charm's 704 "failed" assets.** They are dead on her own site: 24 of a 25-URL sample
  return 404 and one 403, including `/images/arrow.jpg`, which 404s on her live homepage. We cannot
  copy files that do not exist. Retrying them costs about 23 minutes of every fleet run. The right
  change is to remember a permanently-dead asset and report it once as "N images on your own site
  are already broken" — useful to her, and it gives you the run time back. Not built yet.
- **The 8,213-round-trip rehost check.** Diagnosed, not fixed: one Blob `list()` call per asset, per
  store, per run. montrose-edit spends 31 minutes answering "yes, already there" 8,213 times.
